## 1. Why the sponge was never used (diagnosis)

Trial log with the evidence: `pragmabot/data/logs/20260924_131815_1e5b69.jsonl`
("push the small green object towards the red cube", 4 identical failed pushes).

1. **Bare push cannot reach a flat object.** `execute_push` puts the fingertips
   at `table_z + max(0.35 * height, push_height_min_m)` = 0.005 + 0.015 =
   **z 0.020 m** on every attempt; the green T's centroid was at z 0.019–0.020 m.
   The fingers skim or pass over it, so repeating the push can never work. This
   matches the paper's premise ("insufficient contact"), so it was left as is.
2. **Planner prompt had drifted from upstream.** Our failure rule dropped
   upstream's *"whether the scene has been reset or not. Instead, consider
   whether other actions could be taken."* The planner used "scene reset by
   operator" as its reason to repeat the push (see the log's reasoning). The
   PUSH rule also described pushing only with the closed gripper.
3. **Pushing with a held object was impossible.** The executor refused any push
   while holding (`panda_skill_executor.py`), and `execute_push` homes the
   gripper first, which would drop the sponge.

What the paper says (arXiv 2507.16713v2, Sec. IV-C, V-B, Fig. 5b): tool use is
discovered **within one run** from STM after an initial failure; LTM only makes
it first-try in later runs (Table III). Table II allows two attempts; gpt-4o got
67%. We run `claude-sonnet-5`, so parity is not guaranteed.

### Stage 2 — soft-object grasp success (629ec8a)
libfranka reports a grasp as successful only if the finger gap d satisfies
`(width − epsilon_inner) < d < (width + epsilon_outer)`. A sponge squeezes below
that band, so it was reported as a miss while actually held. New parameter
`gripper_min_held_width` (default **0.004 m**): any gap above it counts as
holding; an empty close (~0 mm) still fails.
Side effect: a rigid object caught much narrower than estimated (e.g. an edge)
now counts as grasped instead of retrying. Old behaviour:
`-p gripper_min_held_width:=0.0`.

### Stage 3 — 90° grasp rotation (742ec30)
GraspGen closes the fingers along the grasp frame's **X** (its franka_panda
control points are at x = ±0.053; `docs/GRIPPER_DESCRIPTION.md`). The FR3 hand's
`finger_joint1` slides along the hand's **Y** (`franka_hand.xacro`, axis 0 1 0).
Poses were sent to MoveIt unconverted, so every grasp closed 90° from the one
GraspGen scored. That's invisible on cubes and was the cause of the banana and
sponge grasp failures; the viewer looked correct because it draws GraspGen's own
gripper model.
Measured on the sponge cloud (9.6 × 4.7 × 3.2 cm): before, fingers closed within
3–34° of the long axis (~82 mm for most, more than the 80 mm hand); after,
across the short side (21–26 mm).
- `grasp_transform.graspgen_to_hand()` converts only the poses sent to IK/MoveIt
  (picking the ±90° turn that needs less wrist rotation). Ranking, width and
  centring stay in GraspGen's convention; the cross-axis preference was already
  correct and now actually takes effect on the robot.
- Joint-limit prefilter: before dropping a candidate, it tries the
  finger-swapped (180°) pose, which is the same grasp for this hand.
- **This changes wrist (joint 7) configurations for cube picks too.** A plain
  cube-pick regression check has not been done yet (see Open items).

### Stage 4 — width gate on curved objects (13aed37)
`max_object_span` was measured over the whole cloud along the finger axis, so a
banana's bow was added to its ~4.5 cm thickness (67–101 mm) and every good
cross-grasp was rejected as "too large for this gripper". It's now measured
only over points within `span_slab_half_width_m` (default **0.02 m**) of the
grasp. On the logged banana, all 6 tilt-passing candidates pass (30–45 mm local
span), where 2 did before. An 88 mm cup is still rejected (~78 mm local).
Old behaviour: `-p span_slab_half_width_m:=0.0`.

### Stage 5 — live grasp viewer (0750471)

redraws when they change. Reloading the browser shows the current object. It

## 3. Bowl: why it still fails, and what researchers do

Blue bowl, 17 × 10.4 cm, top at z 0.025 m. GraspGen's confident grasps
(conf ≥ 0.7) are angled rim grasps: median 72° from vertical, the steepest 5%
at about 33°. With the 12° tilt gate, only 3 of 1200 survive, all weak attempts
to grab the whole bowl across (correctly rejected as too wide).

| max tilt | confident grasps | pass width + span |
|---|---|---|
| 12° (default) | 0 | 0 |
| 20° | 7 | 0 |
| 30° | 30 | 2 |
| 40° | 76 | 31 |

GraspGen authors (paper Sec. real-robot experiments; repo README) use no angle
limit: they take the top-100 grasps and give them all to cuRobo (NVBlox scene)
as a goal set; the planner drops colliding or IK-infeasible ones. The repo also
has a point-cloud collision check (`scripts/demo_scene_pc.py
--filter_collisions`). Our tilt gate is a rough stand-in for that, because
MoveIt only knows about the table.

- **Option A (chosen for now):** bowl tests only, run the bridge with
  `-p max_grasp_tilt_deg:=40.0`; cubes keep 12°. No code change.
- **Option B (not done):** replace the tilt gate with a gripper-vs-cloud/table
  collision check plus the existing IK prefilter. General, but it changes every
  pick, so it should be a separate stage that is off by default.

## 5. Test protocol for the sponge STM test

Scene: red cube (left), small green T (middle), sponge (right, clear space).

| Stage | Bridge extra param | Instruction in the UI | Pass if |
|---|---|---|---|
| 1 — mechanics, safe height | `tool_push_clearance_m:=0.02` | `pick up the yellow sponge, then push the small green object towards the red cube` | Pick closes across the sponge's short side; push log says `pushing with the held object, its lowest point at z=0.025 m` |
| 2 — real height | *(none, 4 mm)* | same | Green T moves toward the cube; sponge doesn't grind or trip force limits |
| 3 — the STM test | *(none)* | `push the small green object towards the red cube` | Attempt 1 bare push fails → attempt 2 picks the sponge and pushes with it. Score as success within 2 attempts; run ~5 trials |

Rules for every trial:
- Stand at the e-stop for the first held-object push and the first 40° bowl pick.
- Empty the gripper between trials (utility command above): the next task's
  homing drops whatever is held.
- "yellow sponge" was ambiguous once (two detections); the planner recovered with
  "right yellow sponge". One failed step before the pick is normal.

Status: Stage 1 of this protocol **worked** (sponge picked, pushed at 2 cm).
